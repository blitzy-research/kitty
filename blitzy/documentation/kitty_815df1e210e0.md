## Section 1 — Which language does the runtime heavy lifting, and where does performance come from? (OBJ-1)

**Direct answer.** **Python is the control / orchestration layer; the performance-critical work runs in native C — compiled into a single CPython extension, `kitty.fast_data_types` — and on the GPU via GLSL shaders.** kitty's speed therefore comes from the native core plus GPU offload, not from Python. The Python you see under `kitty/*.py` wires the program together (argument parsing, config, layout policy, glue), while the hot paths (VT parsing, the screen/grid model, GPU rendering, font rasterization, and the PTY I/O loop) live in the C extension and the shaders. Go (`tools/`) is a large, mostly *independent* body that is compiled into a separate `kitten` binary and does not run inside the terminal's per-frame hot loop.

### 1.2 The runtime wiring: a native launcher boots CPython, which loads the C core

kitty ships a **native C launcher** that embeds a CPython interpreter and then hands control to Python, which in turn imports the compiled C core. The launcher constructs the extension directory and Python home and boots the interpreter:

```text
kitty/launcher/main.c
147: run_embedded(RunData *run_data) {
148:     bypy_pre_initialize_interpreter(false);
155:     int num = snprintf(extensions_dir_full, PATH_MAX, "%s/%s/kitty-extensions", run_data->exe_dir, python_relpath);
161:     num = snprintf(python_home_full, PATH_MAX, "%s/%s/python%s", run_data->exe_dir, python_relpath, PYVER);
```

The C core that Python loads is **one** CPython extension module, defined by a single `PyModuleDef` whose name is `fast_data_types`:

```text
kitty/data-types.c
467: static struct PyModuleDef module = {
468:     .m_base = PyModuleDef_HEAD_INIT,
469:     .m_name = "fast_data_types",   /* name of module */
470:     .m_doc = NULL,
471:     .m_size = -1,
472:     .m_methods = module_methods
```

There are **49** top-level C translation units (`ls kitty/*.c | wc -l` → 49) — e.g. `screen.c`, `graphics.c`, `shaders.c`, `fonts.c`, `child-monitor.c`, `vt-parser.c`, `simd-string-128.c`, `simd-string-256.c` — and they all register their functions and constants into that **single** `fast_data_types` module. That is why Sections 3 and 4 both collapse onto the same missing `.so`: it is the one native object the whole Python layer (and the kittens) import from.

**Observed corroboration (and how the VCS stamp is produced).** Once built, the module loads from the compiled object and exposes a build-stamped VCS revision, `KITTY_VCS_REV`. That the module resolves to the compiled `.so` is directly observable:


`KITTY_VCS_REV` is **build/config-dependent** — it is a function of *when* the extension was compiled, not a fixed property of the checkout — so, per the run-first canonical-build discipline, it is read here from a freshly built extension and the reproducible claim below is stated as an **invariant** rather than a frozen hash.

**The mechanism (stable, grounded in `setup.py`).** `KITTY_VCS_REV` is **not** read from the source at import time — it is **stamped into the binary at build time from `git rev-parse HEAD`**. `setup.py`'s `get_vcs_rev()` shells out to `git rev-parse HEAD`, and when `kitty/data-types.c` is compiled that value is injected as the `KITTY_VCS_REV="…"` preprocessor define (two exact, non-elided excerpts):

## Section 2 — What role do the GLSL shader files play, and how central are they? (OBJ-2)

**Direct answer.** The **13** `kitty/*.glsl` files **are** the "GPU accelerated" rendering pipeline. They are not decoration or an optional feature — they are the actual programs kitty uploads to and runs on the GPU to draw everything you see: the terminal grid (text + cursor), window/pane borders, inline images, background images, and the window tint overlay. They are bundled into the build and are compiled and *linked into OpenGL programs at runtime*, once per OS window at startup. If they fail to link, kitty raises an error and cannot render — that is how central they are.

The largest by far are the cell shaders (`cell_vertex.glsl` 233 lines, `cell_fragment.glsl` 204 lines) — the terminal-grid path, which is the core hot path.

The helper classification is grounded in code, not guessed (see 2.4): the build's shader loop keys on the `_vertex` / `_fragment` suffix, and the Python shader layer resolves kitty's own `#pragma kitty_include_shader <...>` directives — the three helpers have no `_vertex`/`_fragment` suffix and are pulled in via `#pragma kitty_include_shader` by the cell and graphics shaders (shown by grep in §2.4).

```text
    for (Py_ssize_t i = 0; i < PyTuple_GET_SIZE(sources); i++) {
        PyObject *temp = PyTuple_GET_ITEM(sources, i);
        if (!PyUnicode_Check(temp)) { PyErr_SetString(PyExc_TypeError, "shaders must be strings"); return false; }
        c_sources[i] = PyUnicode_AsUTF8(temp);
    }
    GLuint shader_id = compile_shaders(shader_type, PyTuple_GET_SIZE(sources), c_sources);
    if (shader_id == 0) return false;
    glAttachShader(program_id, shader_id);
    glDeleteShader(shader_id);
    return true;
}
```

## Section 3 — What is missing when the entry point is run directly, and how is Python wired to the native core? (OBJ-3)
