# How Kitty's `diff` kitten compares files and directories

> A runtime‑grounded onboarding walkthrough, written **after** building and running the
> real `kitten diff` command‑line entry point and capturing its output.
>
> **How to read the evidence in this document.** There are two kinds of captured evidence,
> and they are treated differently so nothing is overstated:
>
> 1. **Byte‑level output** (command stdout/stderr, exit codes, `md5sum`/`cmp`/`wc`/`ls`
>    output, crash stacks, ThreadSanitizer reports, and the decoded terminal escape‑code
>    scans) is shown **complete and unedited** — the exact bytes the command produced, with
>    the exact command that produced it. Where a byte is not printable it is shown in an
>    explicitly labelled hex/escaped form.
> 2. **Full‑screen TUI screens.** `kitten diff` is a full‑screen terminal application that
>    emits cursor‑addressing escape codes, not a plain line stream. To show what actually
>    appears on screen, the raw PTY byte stream is replayed through a small, deterministic,
>    **included** VT grid renderer (`screen_render.py`, listed in
>    [Reproduction](#environment--reproduction)). Every such block is therefore labelled
>    **“rendered screen grid”** rather than “raw output”; the raw byte stream and the
>    renderer are both reproducible, so the grid can be regenerated byte‑for‑byte. Trailing
>    blank screen rows and the `:` status/command line at the bottom of the 40‑row terminal
>    are noted where trimmed.
>
> Every factual claim cites a specific `file:line` / function / struct in the source.
> Statements that could only be read from the code and could **not** be forced through the
> real CLI are explicitly labelled **_(inferred)_** or **_(not reproduced)_**.

## Orientation: the runtime is Go, not Python

Although the kitten *looks* like it lives in Python (`kittens/diff/main.py`), that Python
file only defines the configuration schema and the CLI `--help` text. Its `main()` is a
dead end that deliberately refuses to run:

```python
# kittens/diff/main.py
def main(args: List[str]) -> None:                       # L13
    raise SystemExit('Must be run as kitten diff')       # L14
```

All of the behavior the seven questions ask about — directory collection, rename
detection, caching, parallel highlighting, binary/image handling, the asynchronous
runtime pipeline, and the diff algorithm — is implemented in the **Go** sources under
`kittens/diff/*.go`, compiled into the single `kitten` binary. Consequently, every
observation in this document was produced by building that binary and running
`kitten diff LEFT RIGHT` (files or directories) — the one canonical entry point. No Go
unit test, remote‑control hook, debug interface, or hand‑written diff was used as a
source of truth; where a value could not be forced through the real path it is marked
_(inferred)_.

### How the full‑screen TUI was captured (the harness and the grid renderer)

`kitten diff` is a full‑screen terminal application: it emits cursor‑addressing escape
codes, not a plain line stream, and it enables the kitty keyboard protocol
(report‑all‑keys), so a raw `q`/`Ctrl‑C` is treated as literal text and will **not** quit
— the quit key must be sent as the escape sequence `ESC[113u`. It also divides by the
terminal cell size, so the pseudo‑terminal must have a **real**, non‑zero winsize
(rows, cols, and *pixel* width/height) or `loop.update_screen_size`
(`tools/tui/loop/run.go`) divides by zero.

A few small, deterministic, **temporary** Python tools (removed at the end) implement this.
The two PTY harnesses (`pty_run.py` and `pty_run_stderr.py`) only supply the terminal and
the quit key; the program under the PTY is always the real `kitten diff` CLI. All of these
tools — the two harnesses, the grid renderer (`screen_render.py`), and the two byte‑level
scanners (`scan_colors.py`, `scan_graphics.py`) — are listed here in full so every rendered
screen below is reproducible.

**`pty_run.py`** — opens a PTY with a 40×120 char / 1440×800 px winsize, `exec`s the
command, waits, sends `ESC[113u`, and writes the raw byte stream:

```python
import os, sys, pty, termios, fcntl, struct, select, time, signal
def main():
    wait_s = float(sys.argv[1]); out_path = sys.argv[2]
    assert sys.argv[3] == "--"; cmd = sys.argv[4:]
    rows, cols, xpix, ypix = 40, 120, 1440, 800   # default winsize
    ws = os.environ.get("PTY_WINSIZE")             # optional <rows>x<cols>x<xpix>x<ypix> override
    if ws:
        rows, cols, xpix, ypix = (int(v) for v in ws.split("x"))
    pid, fd = pty.fork()
    if pid == 0:                                   # child: pty.fork() already did setsid +
        winsize = struct.pack("HHHH", rows, cols, xpix, ypix)  # made slave the controlling tty
        fcntl.ioctl(0, termios.TIOCSWINSZ, winsize)
        env = dict(os.environ); env["TERM"] = "xterm-256color"
        os.execvpe(cmd[0], cmd, env); os._exit(127)
    fcntl.ioctl(fd, termios.TIOCSWINSZ, struct.pack("HHHH", rows, cols, xpix, ypix))
    buf = bytearray(); deadline = time.time() + wait_s; sent_quit = False; status = None
    quit_seq = b"\x1b[113u"                        # 'q' under the kitty keyboard protocol
    while True:
        timeout = deadline - time.time()
        if timeout <= 0:
            if not sent_quit:
                try: os.write(fd, quit_seq)
                except Exception: pass
                sent_quit = True; deadline = time.time() + 0.8; continue
            break
        r, _, _ = select.select([fd], [], [], max(0.02, min(timeout, 0.2)))
        if fd in r:
            try: data = os.read(fd, 65536)
            except OSError: break
            if not data: break
            buf.extend(data)
    try: os.write(fd, quit_seq)
    except Exception: pass
    for _ in range(100):
        try:
            wpid, st = os.waitpid(pid, os.WNOHANG)
            if wpid == pid: status = st; break
        except ChildProcessError: break
        time.sleep(0.02)
    if status is None:
        try: os.kill(pid, signal.SIGKILL)
        except Exception: pass
        try: _, status = os.waitpid(pid, 0)
        except Exception: status = 0
    try: os.close(fd)
    except Exception: pass
    open(out_path, "wb").write(bytes(buf))
    ec = os.WEXITSTATUS(status) if (status is not None and os.WIFEXITED(status)) else -1
    sys.stderr.write("raw_bytes=%d child_exit=%d\n" % (len(buf), ec))
main()
```

**`pty_run_stderr.py`** — a variant of `pty_run.py` used only for Q4. It keeps the child's
**stderr on a separate pipe** (instead of letting it merge into the PTY) so a Go panic or
`-race` report can be captured cleanly, apart from the rendered screen, and it writes the
`raw_bytes` / `child_exit` status line to a `.info` **sidecar** file (consumed below by
`cat …info`) rather than to its own stderr:

```python
import os, sys, pty, termios, fcntl, struct, select, time, signal
def main():
    wait_s = float(sys.argv[1]); out_raw = sys.argv[2]; out_err = sys.argv[3]
    assert sys.argv[4] == "--"; cmd = sys.argv[5:]
    rows, cols, xpix, ypix = 40, 120, 1440, 800
    ws = os.environ.get("PTY_WINSIZE")
    if ws:
        rows, cols, xpix, ypix = (int(v) for v in ws.split("x"))
    mfd, sfd = pty.openpty()                        # master/slave PTY for stdin+stdout
    er, ew = os.pipe()                              # separate pipe for the child's stderr
    pid = os.fork()
    if pid == 0:                                    # child
        os.setsid()
        fcntl.ioctl(sfd, termios.TIOCSCTTY, 0)      # make the PTY slave the controlling tty
        os.dup2(sfd, 0); os.dup2(sfd, 1); os.dup2(ew, 2)   # stdin/stdout->PTY, stderr->pipe
        for f in (mfd, sfd, er, ew):
            try: os.close(f)
            except OSError: pass
        fcntl.ioctl(0, termios.TIOCSWINSZ, struct.pack("HHHH", rows, cols, xpix, ypix))
        env = dict(os.environ); env["TERM"] = "xterm-256color"
        os.execvpe(cmd[0], cmd, env); os._exit(127)
    os.close(sfd); os.close(ew)
    fcntl.ioctl(mfd, termios.TIOCSWINSZ, struct.pack("HHHH", rows, cols, xpix, ypix))
    buf = bytearray(); errbuf = bytearray()
    deadline = time.time() + wait_s; sent_quit = False; status = None
    quit_seq = b"\x1b[113u"; fds = [mfd, er]
    def drain(fd, sink):
        try: d = os.read(fd, 65536)
        except OSError: d = b""
        if d: sink.extend(d)
        return d
    while True:
        timeout = deadline - time.time()
        if timeout <= 0:
            if not sent_quit:
                try: os.write(mfd, quit_seq)
                except Exception: pass
                sent_quit = True; deadline = time.time() + 0.8; continue
            break
        r, _, _ = select.select(fds, [], [], max(0.02, min(timeout, 0.2)))
        if mfd in r: drain(mfd, buf)
        if er in r: drain(er, errbuf)
    try: os.write(mfd, quit_seq)
    except Exception: pass
    for _ in range(200):                            # keep draining while the child finishes
        r, _, _ = select.select(fds, [], [], 0.02)
        got = False
        if mfd in r: got = bool(drain(mfd, buf)) or got
        if er in r:  got = bool(drain(er, errbuf)) or got
        try:
            wpid, st = os.waitpid(pid, os.WNOHANG)
            if wpid == pid: status = st; break
        except ChildProcessError: break
        if not got: time.sleep(0.01)
    if status is None:
        try: os.kill(pid, signal.SIGKILL)
        except Exception: pass
        try: _, status = os.waitpid(pid, 0)
        except Exception: status = 0
    while True:                                     # final flush of the stderr pipe (EOF)
        r, _, _ = select.select([er], [], [], 0.1)
        if er in r:
            if not drain(er, errbuf): break
        else: break
    for f in (mfd, er):
        try: os.close(f)
        except Exception: pass
    open(out_raw, "wb").write(bytes(buf))
    open(out_err, "wb").write(bytes(errbuf))
    ec = os.WEXITSTATUS(status) if (status is not None and os.WIFEXITED(status)) else -1
    info = "raw_bytes=%d child_exit=%d" % (len(buf), ec)
    info_path = (out_raw[:-4] if out_raw.endswith(".raw") else out_raw) + ".info"
    open(info_path, "w").write(info + "\n")          # sidecar consumed by `cat …info`
main()
```

**`screen_render.py`** — replays the raw stream into a 40×120 grid, interpreting cursor
addressing (`CUP`), erase (`ED`/`EL`), `CR`/`LF`/`BS`/`TAB`, and cursor moves, and
**discarding** SGR colors, the kitty keyboard‑protocol pushes/pops, APC graphics
sequences (which begin with the bytes `ESC _ G` and end with `ESC \`), OSC and DCS. The
result is the final **visible** text grid:

```python
import sys, re
def render(data: bytes, rows=40, cols=120):
    grid = [[" "]*cols for _ in range(rows)]; cr=cc=0
    text = data.decode("utf-8", "replace"); i=0; n=len(text)
    while i < n:
        ch = text[i]
        if ch == "\x1b":
            if i+1 < n and text[i+1] == "[":
                m = re.match(r"\x1b\[([0-9;:?<>]*)([ -/]*)([@-~])", text[i:])
                if not m: i+=1; continue
                params, final = m.group(1), m.group(3); i += m.end()
                nums = [int(p) for p in re.findall(r"\d+", params)] if params else []
                if final in "Hf":
                    r=(nums[0]-1) if nums else 0; c=(nums[1]-1) if len(nums)>1 else 0
                    cr=max(0,min(rows-1,r)); cc=max(0,min(cols-1,c))
                elif final == "J":
                    mode = nums[0] if nums else 0
                    if mode in (2,3): grid=[[" "]*cols for _ in range(rows)]; cr=cc=0
                    elif mode == 0:
                        for c in range(cc,cols): grid[cr][c]=" "
                        for r in range(cr+1,rows):
                            for c in range(cols): grid[r][c]=" "
                    elif mode == 1:
                        for r in range(cr):
                            for c in range(cols): grid[r][c]=" "
                        for c in range(cc+1): grid[cr][c]=" "
                elif final == "K":
                    mode = nums[0] if nums else 0
                    if mode == 0:
                        for c in range(cc,cols): grid[cr][c]=" "
                    elif mode == 1:
                        for c in range(cc+1): grid[cr][c]=" "
                    elif mode == 2:
                        for c in range(cols): grid[cr][c]=" "
                elif final=="A": cr=max(0,cr-(nums[0] if nums else 1))
                elif final=="B": cr=min(rows-1,cr+(nums[0] if nums else 1))
                elif final=="C": cc=min(cols-1,cc+(nums[0] if nums else 1))
                elif final=="D": cc=max(0,cc-(nums[0] if nums else 1))
                elif final=="G": cc=max(0,min(cols-1,(nums[0]-1) if nums else 0))
                elif final=="d": cr=max(0,min(rows-1,(nums[0]-1) if nums else 0))
                continue                             # SGR 'm', kbd 'u', modes 'h'/'l': ignored
            elif i+1<n and text[i+1]=="]":
                m=re.match(r"\x1b\].*?(\x07|\x1b\\)",text[i:],re.S); i+=(m.end() if m else 2); continue
            elif i+1<n and text[i+1]=="_":
                m=re.match(r"\x1b_.*?\x1b\\",text[i:],re.S); i+=(m.end() if m else 2); continue
            elif i+1<n and text[i+1]=="P":
                m=re.match(r"\x1bP.*?\x1b\\",text[i:],re.S); i+=(m.end() if m else 2); continue
            else: i+=2; continue
        elif ch=="\r": cc=0; i+=1; continue
        elif ch=="\n": cr=min(rows-1,cr+1); i+=1; continue
        elif ch=="\b": cc=max(0,cc-1); i+=1; continue
        elif ch=="\t": cc=min(cols-1,(cc//8+1)*8); i+=1; continue
        elif ch<" ": i+=1; continue
        else:
            if 0<=cr<rows and 0<=cc<cols: grid[cr][cc]=ch
            cc=min(cols-1,cc+1); i+=1; continue
    lines=[ "".join(row).rstrip() for row in grid ]
    while lines and lines[-1].strip()=="": lines.pop()
    return "\n".join(lines)
if __name__ == "__main__":
    raw=open(sys.argv[1],"rb").read()
    print(render(raw, int(sys.argv[2]) if len(sys.argv)>2 else 40,
                       int(sys.argv[3]) if len(sys.argv)>3 else 120))
```

Two byte‑level **scanners** are used for the terminal escape codes that the grid renderer
deliberately drops. `scan_colors.py` extracts 24‑bit `SGR` colors (`ESC[38:2:R:G:Bm` and
`ESC[38;2;R;G;Bm`) for the highlighting evidence (Q3/Q4), and `scan_graphics.py` decodes
the kitty **Graphics Protocol** APC commands and classifies them by action
(query/transmit/put/delete/animate) for the image evidence (Q5); its full source is listed
in Q5.

`scan_colors.py` is listed here in full (`scan_graphics.py` appears with the Q5 image
evidence):

```python
#!/usr/bin/env python3
# Extract the distinct 24-bit (truecolor) SGR colors from a raw terminal byte stream,
# separating foreground (SGR parameter 38) from background (SGR parameter 48). Each
# truecolor is introduced by 38/48 followed by a "2" selector and an R,G,B triple.
# kitty/Chroma emit either the colon subparameter form (ESC[38:2:R:G:Bm) or the
# semicolon form (ESC[38;2;R;G;Bm), and several colors may be combined in a single
# ESC[...m; this scanner handles all of them by flattening ':'/';' to one token stream
# and walking it with a small state machine.
#
# Usage: scan_colors.py <raw_path>
import sys, re
def scan(raw):
    fg, bg = set(), set()
    for m in re.finditer(rb"\x1b\[([0-9;:]*)m", raw):        # every SGR (...m) sequence
        toks = [int(t) for t in re.split(rb"[;:]", m.group(1)) if t != b""]
        i = 0
        while i < len(toks):
            t = toks[i]
            if t in (38, 48) and i + 1 < len(toks):
                if toks[i+1] == 2 and i + 4 < len(toks):     # truecolor: 2,R,G,B
                    r, g, b = toks[i+2], toks[i+3], toks[i+4]
                    (fg if t == 38 else bg).add("#%02x%02x%02x" % (r, g, b))
                    i += 5; continue
                if toks[i+1] == 5:                            # 256-color: 5,n -> not 24-bit
                    i += 3; continue
            i += 1
    return sorted(fg), sorted(bg)
if __name__ == "__main__":
    fg, bg = scan(open(sys.argv[1], "rb").read())
    print("distinct 24-bit fg colors: %d" % len(fg))
    print("fg: %s" % fg)
    print("distinct 24-bit bg colors: %d" % len(bg))
    print("bg: %s" % bg)
```

### The `-race` build (used only for Q4)

A second, `-race`‑instrumented build of the same binary — produced through the same
canonical `setup.py` path — was used **only** to localize the concurrency finding in Q4:

```
# Preserve the normal binary, produce a race build to a separate copy, then rebuild
# to restore the normal binary in place. `go build -v` again prints `kitty/tools/cmd`
# when it relinks (nothing when cached); RACE_BUILD_EXIT is 0.
$ cp /app/kitty/launcher/kitten /tmp/kitten-normal    # preserve the normal binary
$ GOFLAGS=-race python3 setup.py ; echo "RACE_BUILD_EXIT=$?"
kitty/tools/cmd
RACE_BUILD_EXIT=0
$ cp /app/kitty/launcher/kitten /tmp/kitten-race      # preserve the race binary
$ python3 setup.py >/dev/null 2>&1                     # rebuild → restores the normal binary in place
```

It is genuinely instrumented. Because the normal build strips symbols (`-s -w`), the two
binaries are distinguished by their embedded ThreadSanitizer runtime strings and their
size, not by `nm`:

```
$ for b in /tmp/kitten-normal /tmp/kitten-race; do
    echo "$b size=$(stat -c%s $b) ThreadSanitizer_strings=$(strings $b | grep -c ThreadSanitizer)"; done
/tmp/kitten-normal size=15945988 ThreadSanitizer_strings=0
/tmp/kitten-race   size=21463300 ThreadSanitizer_strings=10
```

The normal binary carries **0** ThreadSanitizer strings; the race binary carries **10** and
is ~5.5 MB larger.

The final `python3 setup.py` restores a normal (non‑race) binary in place. It is
**functionally identical** to the preserved `/tmp/kitten-normal` (same 15,945,988‑byte size;
identical `--help`/behavior when invoked under the same program name) — the only byte
differences are Go's build‑ID/buildinfo region (observed: 105 bytes near offsets 3,985 and
15.58 M, with the middle content‑hash component of `go tool buildid` identical between the
two). Crucially, `git status --porcelain` on tracked files stays empty throughout, so the
race experiment leaves **no source‑tree change**.

## Q1 — When pointed at two directories, how does it decide "what belongs together"?

**Direct answer.** Files are paired **by their path relative to the directory root**. The
kitten walks each directory, records the relative name of every file, and pairs the two
sides on the **set intersection of those relative names**
(`left_names.Intersect(right_names)`, `collect.go:L306`). A paired (common) file is
reported as *changed* when its bytes differ; if the bytes are identical it is *still*
reported when only the file mode differs. Names present on only one side are handled later
as additions/removals/renames (Q2). Identical files (same bytes **and** same mode) are not
shown at all.

### Why (causal explanation)

- The walk that builds the name sets is `walk` (`collect.go:L260`), which uses
  `filepath.WalkDir` (`collect.go:L265`) and records each file's relative name via
  `filepath.Rel(base, path)`, adding it to a `utils.Set[string]` and a name→path map. It
  honours the `conf.Ignore_name` patterns.
- `collect_files(left, right)` (`collect.go:L296`) walks the left tree (`L299`) and the
  right tree (`L303`), then computes the pairing:
  `common_names := left_names.Intersect(right_names)` at **`collect.go:L306`**, iterating
  the common names at `L308`. *(This corrects the architecture note, which cited L308 for
  the intersection; L308 is the `for`‑`range` loop over `common_names` that immediately follows.)*
- For each common name it reads both sides (`data_for_path`) and compares:
  `if ld != rd` (`collect.go:L317`) → `self.add_change` (`collect.go:L319`). This is
  the `changed.txt` and `data.bin` case above.
- If the bytes are identical it falls into the **mode‑only** branch (`collect.go:L321-327`):
  it `os.Stat`s both sides and compares `lstat.Mode() != rstat.Mode()` (`L323`; the source
  comment at `L324` literally reads *"identical files with only a mode change"*), and if
  the modes differ it still calls `add_change` (`L326`). That is exactly `mode_only.sh`,
  which the renderer prints as `Mode changed: -rw-r--r-- to -rwxr-xr-x`
  (`render.go` `lines_for_diff` emits `"Mode changed: %s to %s"` at `render.go:L577`).
- Results are ordered by `finalize()` (`collect.go:L203`), which stable‑sorts entries by
  the relative name recorded in `path_name_map`.
- The top‑level dispatch is `create_collection` (`collect.go:L371`): for directory
  inputs it calls `collect_files` (`L386`); for a single pair of file arguments it calls
  `add_change(left, right)` directly (`L401`); either way it ends with `finalize()`
  (`L403`).

This is the recursive directory diffing documented in `docs/kittens/diff.rst` (see the
cross‑check section).

## Q2 — How does it recognize a rename instead of a delete + a brand‑new file?

**Direct answer.** After pairing common names (Q1), the leftover names are split into
*removed* (left‑only) and *added* (right‑only). The kitten then tries to match each
removed file to an added file using a **two‑stage** test: first their **MD5 hashes** must
be equal, and *then* their **full byte contents** must be equal. Only if **both** hold is
it reclassified as a rename (`add_rename`); otherwise it stays a removal plus an addition.
The second, full‑byte stage exists specifically to defeat MD5 hash collisions.

- `removed := left_names.Subtract(common_names)` (`collect.go:L332`) and
  `added := right_names.Subtract(common_names)` (`collect.go:L333`).
- An MD5 is computed for every added path (`hash_for_path`, gathered at `collect.go:L336`)
  and every removed path (`collect.go:L342`). `hash_for_path` (`collect.go:L106`) computes
  an `md5` digest and memoizes it in `hash_cache`.
- The rename‑matching block is `collect.go:L347-364`: for each removed hash it scans the
  added hashes (`L349`); the **first stage** is `if ah == rh` (`collect.go:L350`, MD5
  equal); the **second stage** re‑reads both files' bytes (`ld`, `rd` via `data_for_path`,
  `L351-352`) and requires `if ld == rd` (`collect.go:L353`). Only then does it call
  `self.add_rename(...)` (`collect.go:L354`) and remove that name from the added set with
  `added.Discard(n)` (`collect.go:L355`).
- If no confirmed match is found, the removed file becomes `self.add_removal(...)`
  (`collect.go:L362`); every leftover added name becomes `self.add_add(...)`
  (`collect.go:L366`). `add_rename` itself is defined at `collect.go:L175`.

For the collision fixture, stage one (`L350`) is **true** (MD5s match) but stage two
(`L353`) is **false** (bytes differ at char 20), so control falls through to
removal + add — precisely the observed two‑entry output. This is *why* the guard needs the
`ld == rd` full‑byte comparison and not the hash alone.

## Q3 — How does caching work across layers, and how does it stay efficient?

**Direct answer.** Every expensive per‑file computation is memoized in one of **seven
path‑keyed caches** created **once per process** by `init_caches()` (`collect.go:L26`,
called from `main()` at `main.go:L114`). All seven are constructed with the same nominal
capacity `const sz = 4096` (`collect.go:L29`), **but only four of them actually enforce that
cap** — the four read through `GetOrCreate` — while the other three (read through
`MustGetOrCreate`, or written through `Set`) ignore `max_size` entirely and grow **unbounded**
for the life of the process. The caches are **not a single linear stack**; they form a small
**dependency graph keyed by file path**, rooted at the raw‑bytes cache. Because the process is
short‑lived (one diff, then exit) each file is read, sized, MIME‑sniffed, UTF‑8‑classified,
line‑split, hashed, and syntax‑highlighted **at most once**, and every later stage (diffing,
rendering, re‑rendering after highlight/image events) reuses those results by path.
Highlighting is additionally *gracefully optional*: the render path asks for highlighted lines
but transparently falls back to plain lines when highlighting has not yet finished.

### The seven caches (all by name)

Declared at `collect.go:L20-24`, constructed at `collect.go:L30-36` (all with `sz = 4096`).
The **Accessor(s)** column determines whether the 4096 cap is actually honored:

| # | Cache | Value type | Memoizes | Accessor(s) | Cap enforced? |
|---|-------|-----------|----------|-------------|---------------|
| 1 | `size_cache` | `int64` | file size in bytes | `size_for_path` → `GetOrCreate` (`collect.go:L73`) | **Yes** (bounded) |
| 2 | `data_cache` | `string` | raw file contents (`os.ReadFile`) | `data_for_path` → `GetOrCreate` (`collect.go:L66`) | **Yes** (bounded) |
| 3 | `hash_cache` | `string` | MD5 digest of the bytes | `hash_for_path` → `GetOrCreate` (`collect.go:L107`) | **Yes** (bounded) |
| 4 | `lines_cache` | `[]string` | sanitized text lines | `lines_for_path` → `GetOrCreate` (`collect.go:L139`) | **Yes** (bounded) |
| 5 | `mimetypes_cache` | `string` | guessed MIME type | `mimetype_for_path` → `MustGetOrCreate` (`collect.go:L51`) | **No** (unbounded) |
| 6 | `is_text_cache` | `bool` | text‑vs‑binary verdict | `is_path_text` → `MustGetOrCreate` (`collect.go:L87`) | **No** (unbounded) |
| 7 | `highlighted_lines_cache` | `[]string` | Chroma‑highlighted lines | `Set` on write (`highlight.go:L224`), `Get` on read (`collect.go:L153`) | **No** (unbounded) |

All seven are instances of the generic `LRUCache[K comparable, V any]`
(`tools/utils/cache.go:L13`) with fields `data map[K]V`, `lock sync.RWMutex` (`cache.go:L15`),
`max_size int` (`cache.go:L16`) and `lru *list.List` (`cache.go:L17`). **"LRU" is a misnomer
for how these caches actually behave** — the four methods differ sharply:

- **`Get`** (`cache.go:L25-30`) takes an `RLock`, reads `data[key]`, returns. It **never
  touches the `lru` list**, so *reading* an entry does **not** refresh its recency.
- **`GetOrCreate`** (`cache.go:L39-58`) is the only bounded path. On a miss it calls `create`,
  then under a write `Lock` stores the value, does `lru.PushFront(key)` (`cache.go:L50`), and —
  only here — evicts when over capacity: `if self.max_size > 0 && self.lru.Len() > self.max_size`
  it removes `self.lru.Back()` and deletes it (`cache.go:L51-53`). Because the push‑front happens
  **only on a miss/create** (never on a hit, and `Get` never reorders), eviction is by
  **insertion order (FIFO)**, not by least‑recent *use*. Caches #1–#4 use this path.
- **`Set`** (`cache.go:L32-37`) writes `data[key]=val` under an **`RLock`** (not a write lock)
  and **never touches `lru` or `max_size`** — so cache #7 is unbounded, and that map write under
  a *read* lock is the concurrency finding examined in Q4.
- **`MustGetOrCreate`** (`cache.go:L60-72`) stores under a write `Lock` but **never touches
  `lru` or `max_size`** — so caches #5 and #6 are unbounded.

**The dependency graph (keyed by path), not a stack.** `data_cache` is the root: `hash_cache`'s
create func calls `data_for_path` then `md5.Sum` (`collect.go:L108-112`); `lines_cache`'s calls
`data_for_path` then `sanitize`/`text_to_lines` (`collect.go:L140-144`); `is_text_cache`'s calls
both `is_image` (→ `mimetypes_cache`, `collect.go:L88`) and `data_for_path` for
`utf8.ValidString` (`collect.go:L98-102`). `highlighted_lines_cache` is fed by the highlighter
and read against `lines_cache` (the length guard below). `size_cache` is independent (`os.Stat`).

### The graceful highlighted‑vs‑plain fallback

`highlighted_lines_for_path` (`collect.go:L148`) is the layer that ties the plain‑line
cache to the highlighted‑line cache:

1. It fetches the plain lines first (`collect.go:L149`).
2. It returns cached highlighted lines **only** when they exist *and* their count matches
   the plain lines: `if ans, found := highlighted_lines_cache.Get(path); found && len(ans) ==
   len(plain_lines)` → return `ans` (`collect.go:L153-154`).
3. Otherwise it returns the plain lines (`collect.go:L156`).

That miss branch (`Get` returning "not yet cached", so plain text is used) is not merely
read from the code — it is **observed** in the `-race` read stack in Q4, where the main
goroutine calls `highlighted_lines_for_path → LRUCache.Get` (`collect.go:L153`,
`cache.go:L27`) *during the first render, before the highlight workers have populated the
cache*. What is **_(inferred)_** is only the exact sub‑perceptible timing of an isolated
"plain frame" for small inputs: for small diffs the highlight goroutine wins the race so
quickly that a cleanly‑isolated plain‑only frame is not visible to the harness even at a
zero wait; the fallback path is nonetheless exercised (per the observed `Get` miss).

### Why it stays efficient

Because the caches form a dependency graph rooted at the raw bytes, a hit on an upper cache
avoids *all* the work below it: a hit on `data_cache` spares the disk re‑read that
`hash_cache`, `lines_cache` and `is_text_cache` all build on, and a hit on `lines_cache`
spares the re‑split that highlighting builds on. The path key means the collection, diff,
render and re‑render stages share the same memoized artifacts. Memory is bounded **only for
the four `GetOrCreate` caches (#1–#4)** — their FIFO‑by‑insertion eviction fires when a cache
exceeds 4096 entries (`cache.go:L51-53`). The three `MustGetOrCreate`/`Set` caches (#5–#7)
are **unbounded**, which is safe in practice only because the process handles a single diff
and then exits.

**Honesty note (observed vs inferred).** Eviction itself is **_(inferred)_** — code‑read only —
because every fixture had far fewer than 4096 distinct paths, so the eviction branch
(`cache.go:L51-53`) never fired at runtime. Per‑access hit/miss *counters* are not exposed
through the CLI, so any statement about exact hit *ratios* is likewise **_(inferred)_**. The
genuinely observable proxies are: the deterministic byte‑identical repeated output (above),
the stable highlighted color set once highlighting completes (above), and the `-race`
`Get`/`Set` stacks in Q4 that show the caches being consulted and populated by path.

## Q4 — How does syntax highlighting run in parallel without "stepping on itself"?

**Direct answer.** Highlighting is dispatched across a worker pool (up to `runtime.NumCPU()`
goroutines), and the *dispatch* design is careful: each file path is enqueued exactly once
on a shared channel and consumed by exactly one worker, and each worker writes its result
back under a **distinct path key** — so no two highlighters ever target the same logical
cache key. **However, observed at scale, it *does* step on itself.** The write‑back uses
`LRUCache.Set`, which — surprisingly — mutates the underlying Go map while holding a
**read** lock (`RLock` at `cache.go:L33`, the map write at `cache.go:L34`), not a write lock.
Because Go maps are unsafe for concurrent mutation *even to different keys*, running the
kitten against a large corpus produces a **reproducible fatal crash** (and, under `-race`, a
data‑race report) as the highlight workers write and the main render goroutine reads the same
map concurrently.
Per‑key isolation is real but insufficient; the physical Go‑map access is not serialized.

### The dispatch mechanism (why it is *designed* not to contend on keys)

- `highlight_all(paths)` (`highlight.go:L217`) fans work out with
  `ctx.Parallel(0, len(paths), ...)` (`highlight.go:L219`). Each worker takes
  `path := paths[i]` (`L221`), calls `highlight_file(path)` (`L222`), and writes the result
  keyed by path: `highlighted_lines_cache.Set(path, text_to_lines(raw))` (`highlight.go:L224`).
- The worker pool `(*images.Context).Parallel` (`tools/utils/images/utils.go:L27`) sizes
  `procs` from `NumberOfThreads()` else `runtime.NumCPU()` (`utils.go:L33-35`), capped to
  the item count (`utils.go:L37-39`). It creates a **buffered** channel
  `c := make(chan int, count)` (`utils.go:L41`), enqueues **each index exactly once**
  (`utils.go:L42-44`), then **closes** it (`utils.go:L45`), and starts `procs` goroutines
  (`utils.go:L50`) that each `range` the *same* channel; `wg.Wait()` (`utils.go:L55`) joins
  them. Because every index is enqueued once and the channel is shared, each path is handed
  to exactly one goroutine — no path is highlighted twice, and results land under unique
  keys. That is the sense in which it is designed "not to step on itself."

### A failed highlight is silently discarded (not retried, not fatal)

The worker body swallows every error from `highlight_file`:

```go
raw, err := highlight_file(path)   // highlight.go:L222
if err == nil {                    // highlight.go:L223  <- error is dropped here
    highlighted_lines_cache.Set(path, text_to_lines(raw))  // highlight.go:L224
}
```

`highlight_file` (`highlight.go:L161`) can fail four ways, each returning a non‑empty `err`:
a read error from `data_for_path` (`L172-174`); **no lexer** matched for the file — after
`lexers.Match` and the `lexers.Analyse` fallback both yield `nil`, it returns
`ErrNoLexer` (`L181-183`); a `lexer.Tokenise` error (`L206-208`); or a
`formatter.Format` error (`L212-214`). When any of these fires, `err != nil`, so the
`if err == nil` guard at `L223` is false and **`Set` is never called** — the path simply gets
no entry in `highlighted_lines_cache`. The `HIGHLIGHT` stage still finishes normally (the
error never propagates out of the worker or the pool), and rendering falls back to plain,
uncolored lines via the `highlighted_lines_for_path` length‑guard described in Q3.

This is observable. A file with an extension Chroma has no lexer for (`.zzq`) and prose
content (so `lexers.Analyse` also returns `nil` → the `ErrNoLexer` branch at `L182`) renders

### Why (root cause)

The `Set` frame in the race report is the smoking gun. `LRUCache.Set` (`cache.go:L32`)
takes a **read** lock — `self.lock.RLock()` (`cache.go:L33`) — and then assigns into the
map at `cache.go:L34`. `Get` also uses `RLock` (`cache.go:L26`). A read lock permits many
holders simultaneously, so it does **not** serialize the map mutation performed in `Set`.
The highlight write‑back path uses `Set` (`highlight.go:L224`), so multiple worker
goroutines can `mapassign` into `highlighted_lines_cache` concurrently, and the main render
goroutine can `mapaccess` it at the same time (via `highlighted_lines_for_path`,
`collect.go:L153`). Go maps forbid concurrent write/write and read/write access **even for
different keys**, so the runtime aborts with the fatal errors above.

In other words: the AAP's expectation that highlighters "never contend for the same cache
key" is *true* — per‑path keying does prevent logical key collisions — but it is
*insufficient*, because the crash is a **physical** Go‑map data race, not a logical
key collision. The honest, observed answer to "does it run in parallel without stepping on
itself?" is: **at small scale yes, but at large scale no — it races and crashes**, and the
`-race` detector localizes it to `Set` writing the map under a read lock (`cache.go:L33-34`).

This same async design is what `docs/kittens/diff.rst` advertises as *asynchronous*
highlighting "for maximum speed" (L15‑16) — the speed and the race have the same origin.

## Q5 — What changes when binary files or images appear alongside plain text?

**Direct answer.** Every path is first *classified*. A path whose MIME type starts with
`image/` is an **image** (`is_image`, `collect.go:L82`); otherwise it is **text** iff its
bytes are valid UTF‑8 (`is_path_text`, `collect.go:L86`, via `utf8.ValidString`,
`collect.go:L102`) — so a non‑UTF‑8 file is **binary**. Only **text‑vs‑text** pairs ever
become real line diffs; images are transmitted to the terminal as pixels using the **kitty
Graphics Protocol** and shown with their dimensions/size; binaries are not diffed at all —
they render as a single `Binary file: <size>` line.

The full source of the scanner used above (referenced from
[Environment & Reproduction](#environment--reproduction)):

```python
#!/usr/bin/env python3
# Decode kitty Graphics Protocol APC sequences from a raw byte stream and classify
# them by ACTION (query/transmit/display/delete/animate), separating capability
# queries and control commands from the actual pixel-carrying transmissions.
#
# Wire format: ESC _ G <control-data> ; <base64-payload> ESC \
# control-data = comma-separated key=value pairs. Action key `a`:
#   q=query, t=transmit(only), T=transmit+display, p=put/display, d=delete,
#   f=frame, a=animate, c=compose. If `a` is absent the default action is transmit.
# Transmission medium key `t`: d=direct(inline base64 pixels), f=regular file,
#   t=temporary file, s=POSIX shared memory. For f/t/s the payload is a base64 path/name.
#
# Usage: scan_graphics.py <raw_path>
import sys, re
from collections import Counter

ACTION_NAMES = {
    "q": "query(a=q)", "t": "transmit(a=t)", "T": "transmit+display(a=T)",
    "p": "put/display(a=p)", "d": "delete(a=d)", "f": "frame(a=f)",
    "a": "animate(a=a)", "c": "compose(a=c)",
}

def main():
    data = open(sys.argv[1], "rb").read()
    # ctrl = bytes up to first ';' or ESC; payload = bytes up to ESC
    seqs = re.findall(rb"\x1b_G([^;\x1b]*);?([^\x1b]*)\x1b\\", data, re.S)
    total = len(seqs)
    actions = Counter()
    more_chunks = 0
    with_payload = 0
    total_payload_bytes = 0
    pixel_carriers = []
    for idx, (ctrl, payload) in enumerate(seqs):
        kv = {}
        for part in ctrl.decode("latin1").split(","):
            if "=" in part:
                k, v = part.split("=", 1)
                kv[k] = v
        a = kv.get("a", "t")
        actions[ACTION_NAMES.get(a, "action a=%s" % a)] += 1
        if kv.get("m") == "1":
            more_chunks += 1
        if payload:
            with_payload += 1
            total_payload_bytes += len(payload)
            # a direct pixel transmission has no medium key t or t=d, and no a=q
            if a != "q" and kv.get("t", "d") == "d":
                pixel_carriers.append((idx+1, len(payload)))
    print("total _G sequences: %d" % total)
    print("by action:")
    for name, cnt in sorted(actions.items()):
        print("  %-24s %d" % (name, cnt))
    print("chunks with m=1 (continuation): %d" % more_chunks)
    print("sequences carrying a base64 payload: %d" % with_payload)
    print("total base64 payload bytes: %d" % total_payload_bytes)
    print("direct pixel-carrying transmissions (seq#: base64 bytes): %s" % pixel_carriers)

if __name__ == "__main__":
    main()
```

### Why (causal explanation)

- **Classification.** `is_image(path)` (`collect.go:L82`) is `strings.HasPrefix(mimetype,
  "image/")` on the MIME type from `mimetype_for_path` (`collect.go:L50`, which calls
  `utils.GuessMimeTypeWithFileSystemAccess`). `is_path_text(path)` (`collect.go:L86`,
  memoized in `is_text_cache` via `MustGetOrCreate`) returns `false` if the path is an
  image (`L88`), `false` for `/dev/null` (detected with `os.Stat` + `os.SameFile`,
  `collect.go:L91-96` — see the edge cases appendix), and otherwise
  `utf8.ValidString(data)` (`collect.go:L102`). So invalid UTF‑8 ⇒ binary.

## Q6 — What happens, end to end, from "compare two directories" to "everything understood"?

**Direct answer.** The pipeline is **asynchronous and event‑driven**. `main()` first does the
synchronous setup — argument‑count check, `set_diff_command`, `init_caches`,
`create_formatters`, operand resolution, a "both dirs or both files" guard — then builds the
TUI event loop, wires its callbacks (`OnInitialize`, `OnWakeup`, `OnResize`, plus the
key/text/mouse handlers) and calls `lp.Run()`. `OnInitialize` runs `Handler.initialize`, which launches **one** background
goroutine that *collects* the two trees and, when done, wakes the main thread. There is
exactly **one guaranteed‑first stage: `COLLECTION`.** Handling the `COLLECTION` result then
launches up to **three concurrent** background stages at once — *diff*, *highlight*, and (only
if the collection contains images) *image‑load* — which run in parallel and post their results
back **in any order** over a buffered channel, each waking the main thread. A **fifth** result
type, `IMAGE_RESIZE`, is posted whenever images must be re‑sized to the current page. The main
thread drains the channel and dispatches by result type: `DIFF` sets `diff_map`, computes
statistics and renders; `HIGHLIGHT`, `IMAGE_LOAD` and `IMAGE_RESIZE` each trigger a re‑render.
Until the first full render (`logical_lines`, `diff_map` and `collection` all non‑nil) a
"Calculating diff, please wait..." placeholder is shown. So the user perceives
`COLLECTION` first and then a diff that *progressively repaints* as highlighting and images
arrive — but after `COLLECTION` there is **no fixed order** among `DIFF`/`HIGHLIGHT`/
`IMAGE_LOAD`; the Q4 read/write data race (main‑goroutine render reading the highlight cache
while a highlight worker writes it) is direct **observed** proof that the `DIFF`‑triggered
render and the `HIGHLIGHT` stage overlap in time.

- **Five result types.** The `ResultType` constants are `COLLECTION` (`ui.go:L25`), `DIFF`

  - `IMAGE_LOAD, HIGHLIGHT` (`ui.go:L272`) → `rerender_diff()` (`ui.go:L273`).

  `diff(jobs, self.current_context_count)` and posts `AsyncResult{rtype: DIFF}`
  (`ui.go:L153-158`). `highlight_all`
  (`ui.go:L179`) launches a goroutine that highlights all text files and posts

changed / was renamed / added / removed* (`COLLECTION`, Q1‑Q2), then — concurrently and in no
fixed order — *how each text file changed* (`DIFF`, Q7), *syntax highlighting* (`HIGHLIGHT`,
Q4), and *image load/resize* (`IMAGE_LOAD`/`IMAGE_RESIZE`, Q5), with the screen progressively
repainted as each completes.

## Q7 — How does the diff algorithm find matching regions while the cache keeps it fast?

**Direct answer.** Which differ is used is chosen by the `diff_cmd` option through
`set_diff_command` (`patch.go:L44`), whose cases are `auto`, `builtin`/`""`, `git`,
`diff`, and *any other string* (a custom command). The default is `auto`, which picks the
first available of **git → diff → builtin**. The `builtin`/`""` differ is an internal
**anchored (a.k.a. "patience") diff** in `diff.go` (`func Diff`, `diff.go:L49`): it finds
matching regions by anchoring on lines that are **unique in both** inputs, giving
`O(n log n)` behavior instead of the classic `O(n²)`. Whatever differ is chosen, per‑file
diffs are computed **in parallel** across the same `Parallel` worker pool (`patch.go:L361`).
How the cache interacts with the diff **depends on the differ**, and this is the key
correction to the earlier draft: **only the builtin differ reads file contents from the
`data_for_path` cache** (`patch.go:L295`, `L299`) and feeds them straight to `Diff`. The
**external** differs (`git`/`diff`/custom) are launched as **subprocesses** (`exec.Command`,
`patch.go:L315`) that receive the file *paths* and **re‑read the files from disk themselves**
— the cache does not serve their file reads. What the cache *does* accelerate for **every**
differ is the **patch‑parsing** step: `do_diff` pulls the left/right line arrays from the
`lines_for_path` cache (`patch.go:L338`, `L342`) to turn the raw unified‑diff text into
structured hunks. So "the cache keeps everything fast" is true — but for external differs it
speeds the *parse*, not the *file read*.

### Why (causal explanation)

- **Differ selection.** The config option is `diff_cmd`, whose default value is `auto`
  (`main.py:L41`); `main.go` reads it and calls `set_diff_command(conf.Diff_cmd)`
  (`main.go:L111`). `set_diff_command(q)` (`patch.go:L44`) switches on the string:
  - `auto` → `find_differ()` (`patch.go:L46-47`), which prefers `git` (`GIT_DIFF`,
    `patch.go:L21`), then `diff` (`DIFF_DIFF`, `patch.go:L22`), then the builtin
    (`find_differ` at `patch.go:L34`).
  - `builtin` or `""` → an empty `diff_cmd = []string{}` (`patch.go:L48-49`), i.e. the
    internal anchored diff.
  - `diff` → `DIFF_DIFF` (`patch.go:L50-51`).
  - `git` → `GIT_DIFF` (`patch.go:L52-53`).
  - any other string → a custom command parsed with `shlex.Split(q)` (`patch.go:L54-59`).
- **The anchored/patience algorithm.** The builtin differ is `func Diff` (`diff.go:L49`).
  Its doc comment (`diff.go:L21-48`) states it diffs on lines that "appear just once in both
  old and new" (unique in both, `L34`), calls this an **"anchored diff because the unique
  lines anchor the chosen matching regions"** (`L35-36`), runs in **`O(n log n)` time instead
  of the standard `O(n²)` time** (`L39-40`), and notes that "some systems call this approach
  a 'patience diff'" (`L42-43`). The unique‑line anchor pairs are computed by `func tgs`
  (`diff.go:L192`).
- **Parallel fan‑out.** `func diff(jobs, context_count)` (`patch.go:L352`) dispatches the
  per‑file jobs by calling `ctx.Parallel` over `len(jobs)` items (`patch.go:L361`) — the **same**
  `Parallel` worker pool as highlighting (Q4) — invoking the per‑file worker `do_diff`
  (`patch.go:L330`) once per job, each result sent over a buffered channel and collected with
  a first‑error‑wins loop (`patch.go:L368-373`). *(This corrects the earlier architecture
  note, which attributed the parallel dispatch to L352 — that line is the `diff()` dispatcher
  function header; the `ctx.Parallel` call itself is at `patch.go:L361`.)*
- **`run_diff`: symlink resolution first, then a builtin/external fork.** `run_diff`
  (`patch.go:L282`) **always** resolves *both* operands with `filepath.EvalSymlinks`
  (`patch.go:L286`, `L290`) **before** choosing a differ — this applies to **every** differ,
  not just git. The in‑code comment (`patch.go:L283-285`) explains why: "*git diff does not
  follow symlinks, while diff does. We want consistent behavior*", so both operands are
  resolved to their targets up front. Then the fork on `len(diff_cmd) == 0` (`patch.go:L294`):
  - **builtin branch** (`diff_cmd` empty): reads both files' bytes from the `data_for_path`
    cache (`patch.go:L295`, `L299`) and calls
    `Diff(path1, data1, path2, data2, num_of_context_lines)` (`patch.go:L303`); an empty
    result means "no differences" (`patch.go:L304-306`).
  - **external branch** (`else`, `patch.go:L308`): substitutes `_CONTEXT_`, appends the two
    resolved paths, and runs `exec.Command(cmd[0], cmd[1:]...)` (`patch.go:L315`) — a **real
    subprocess** (git/diff/custom) that opens and **re‑reads the files from disk itself**. It
    is classified purely by exit code (`patch.go:L319-326`): 0 → identical, 1 → different
    (`patch.go:L321-322`), anything else or an exec failure → error (`patch.go:L324`).
- **`do_diff` + `parse_patch`: the cache accelerates parsing, for every differ.** `do_diff`
  (`patch.go:L330`) calls `run_diff`, and — regardless of which differ produced the raw text —
  fetches the left/right line arrays from the `lines_for_path` cache (`patch.go:L338`, `L342`)
  and hands them to `parse_patch` (`patch.go:L245`). `parse_patch` walks the unified‑diff text
  (`splitlines_like_git`, `patch.go:L248`), starting a new `Hunk` on each `@@ ` header
  (`patch.go:L249-251`) and classifying each body line by its first byte — `+` → `add_line`,
  `-` → `remove_line`, `\` → ignored, else context (`patch.go:L253-266`) — then `finalize`s
  each hunk against the cached line arrays (`patch.go:L269`) to produce the structured
  `Patch{all_hunks: []*Hunk}`. **This** is the sense in which the cache "keeps everything
  fast" for external differs: it never re‑reads files for the *parse*, even though the external
  subprocess re‑read them for the *diff* itself.

**Correcting the earlier draft's symlink claim.** Two mechanisms are involved, and neither is

- **The walk records the symlink as a non‑directory leaf.** `walk` uses `filepath.WalkDir`

  wording.) When bytes are needed, `data_for_path` → `os.ReadFile` (`collect.go:L67`)
  dereferences the link to read the **target's** content.

  happens "only in the git differ path" — that is **wrong**. `filepath.EvalSymlinks`

**Malformed patch text — observed via the documented `-o diff_cmd` override (non‑default
configuration).** The builtin, `git`, and `diff` differs never emit malformed unified‑diff
output, so this branch is genuinely unreachable in default config; but `diff_cmd` is a
**documented** option (default `'auto'`, `main.py:L41`; resolved in `set_diff_command`,
`patch.go:L44-59`) and a custom differ can emit anything. `parse_patch` (`patch.go:L245`) trusts
the differ's format. Two hostile differs, each invoked through the real entry point, expose two
**distinct** real behaviors — **neither** is the benign "parse failure" one might infer:

*Case A — a differ that prints pure garbage (no `@@` hunk headers) and exits 1.* `run_diff`
treats exit 1 as "has changes" (`patch.go:L321-322`) and hands the garbage to `parse_patch`,
which finds no hunks — an empty patch — so the kitten renders **"The files are identical"**,
silently wrong because the files differ:

## Cross‑check against `docs/kittens/diff.rst`

The observed behavior matches the four "Major Features" the official docs advertise
(`docs/kittens/diff.rst`, "Major Features" heading at L8):

| Documented feature | Doc line | Observed here |
|--------------------|----------|---------------|
| Side‑by‑side display | `diff.rst:L13` | Every capture above is two columns (Q1, Q5, Q7) |
| **Asynchronous** syntax highlighting "for maximum speed" | `diff.rst:L15-16` | The async `HIGHLIGHT` stage (Q6) and the parallel worker pool (Q4); the speed and the `-race` crash share this async origin |
| Images even over SSH | `diff.rst:L18` | 17 kitty Graphics‑Protocol APC `_G` sequences transmitted for PNGs (Q5) |
| Recursive directory diffing | `diff.rst:L20` | Name‑intersection pairing over walked trees (Q1) |

Usage is documented as `kitten diff file1 file2` (`diff.rst:L42`) and "You can also pass
directories instead of files to see the recursive diff of the directory contents"
(`diff.rst:L57-58`) — both exercised throughout.

One honest divergence to flag: the docs sell asynchronous highlighting as a pure speed win,
but the runtime observation (Q4) shows that same asynchrony, combined with `LRUCache.Set`
mutating its map under a read lock (`cache.go:L33-34`), produces a reproducible crash on
large corpora. The feature works as documented at ordinary scale; the race is a
scale‑dependent defect, not a documentation error.
