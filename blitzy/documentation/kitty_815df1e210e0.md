# Kitty SSH Kitten — Secure Session Setup & Connection Sharing (branch `kitty_815df1e210e0`)

This document traces, end-to-end and with reproduced runtime evidence, how Kitty's **SSH kitten** sets up a secure remote session and shares/reuses SSH connections — from a user locally running `kitty +kitten ssh host` to the generated bootstrap script executing on the remote host.

It is an **evidence-backed investigation**: every behavioral claim below is paired with the exact command that produced the observation and the verbatim output of *this repository at* HEAD commit `815df1e210e0a9ab4622f5c7f2d6891d7dbeddf1`. The code is the subject matter; nothing in the repository was modified to produce this document.

---

## Critical context an onboarding reader must know first

**1. The SSH-kitten runtime is Go, not Python.** All of the mechanisms discussed here live in `kittens/ssh/main.go`. The Python module `kittens/ssh/main.py` and `kittens/ssh/utils.py` hold **only option/config definitions** — they contain no part of the runtime session-setup pipeline. The Go file is the driver; `kittens/ssh/main.go` imports the generated `kitty` constants package at `[kittens/ssh/main.go:15]` and is what actually assembles the tarball, writes the shared-memory object, generates and encodes the bootstrap script, and spawns `ssh`.

The two file sizes make the split concrete:

```bash

```


The larger Go file is the runtime; the smaller Python file is options only.

**2. The Go kitten cannot be built from a bare checkout.** It requires two build-time-generated artifacts:

- the in-repo Go `kitty` constants package `constants_generated.go` (containing e.g. `SSHControlMasterTemplate`), generated by `gen/go_code.py` at `[gen/go_code.py:599]` via the `setup.py` function `update_go_generated_files` at `[setup.py:1102]`; and
- the embedded shell-integration archive `data_generated.bin`, pulled in by `//go:embed data_generated.bin` at `[tools/tui/shell_integration/data.go:19]`.

Both are produced by `python setup.py build`. This is proven directly by the bare-build failure in **EV0** below.

**3. A live SSH server is NOT required** to observe the mechanisms. The code paths — `make_tarfile`, `bootstrap_script`, `wrap_bootstrap_script`, the shared-memory write/read, the per-shell encoding, and `connection_sharing_args` — are all exercised directly in-process through the Go test package (`package ssh`), which is what the evidence below does.

## Q1 — Shared-memory credential passing

**Mechanism.** Rather than putting the per-session password and the shell-integration payload on the `ssh` command line or in the environment (both observable by other processes), the kitten mints a random password, packs it with the tarball into a JSON blob, and writes that blob into a POSIX shared-memory object created with owner-only permissions. Only the object's *name* travels to the remote side; the remote reads the object once and it is then unlinked.

**Code trace.** In `bootstrap_script` `[kittens/ssh/main.go:422]`:

- A per-session token is minted with `pw, err := secrets.TokenHex()` `[kittens/ssh/main.go:431]`.
- The payload is assembled `[kittens/ssh/main.go:439-442]` as `data := map[string]string{ "tarfile": base64.StdEncoding.EncodeToString(tfd), "pw": pw, "hostname": cd.hostname_for_match, "username": cd.username }` (the tarball is base64-encoded at `[kittens/ssh/main.go:440]`).
- It is serialized with `json.Marshal(data)` `[kittens/ssh/main.go:444]`.
- The shared-memory object is created with `data_shm, err = shm.CreateTemp(fmt.Sprintf("kssh-%d-", os.Getpid()), uint64(len(encoded_data)+8))` `[kittens/ssh/main.go:446]` — note the `kssh-<pid>-` name prefix and the `+8` slack (the writer prepends a 4-byte size; `NUM_BYTES_FOR_SIZE = 4` at `[tools/utils/shm/shm.go:116]`).
- The bytes are written with `shm.WriteWithSize(data_shm, encoded_data, 0)` `[kittens/ssh/main.go:448]`, which writes a 4-byte big-endian length prefix then the data (`WriteWithSize` at `[tools/utils/shm/shm.go:120]`).
- The object name is recorded (along with the password and request id) in `sensitive_data := map[string]string{"REQUEST_ID": cd.request_id, "DATA_PASSWORD": pw, "PASSWORD_FILENAME": cd.shm_name}` `[kittens/ssh/main.go:460]`.
- Read-back on the receiving path is `read_data_from_shared_memory` `[kittens/ssh/main.go:72]`, which delegates to `shm.ReadWithSizeAndUnlink`.

**Observed evidence.** Driving `bootstrap_script` with `dont_create_shm=false` and inspecting the object:

```bash
go test -run TestBlitzyObserveEV6 -v ./kittens/ssh/     # temporary harness, since removed
```

```
EV6>>> shm_name: kssh-40398-FZFPPIJG726JE
EV6>>> stat /dev/shm/kssh-40398-FZFPPIJG726JE -> -rw------- mode=0600
EV6>>> read #1: ok=true bytes=32179
EV6>>> read #2 (after unlink): err=open /dev/shm/kssh-40398-FZFPPIJG726JE: no such file or directory
```

The object name carries the `kssh-<pid>-` prefix from `[kittens/ssh/main.go:446]` (`kssh-40398-…`, pid 40398 this run). The first read returns the 32179-byte JSON payload; the second read fails because the object was unlinked after the first read (the read-once behavior detailed in Q8).

**Rationale.** The credential (`pw`) and the whole tarball never appear in `argv` or the environment — only the shm object *name* is later transmitted (over the tty, see Q9). Because the object is owner-only (`0600`) and read-once, the exposure window for the secret is minimized.

## Q2 — Bootstrap script generation

**Mechanism.** The kitten does not hand-write the remote script inline; it loads a checked-in template (`shell-integration/ssh/bootstrap.sh` or `.py`), then substitutes a set of named placeholders (request id, password filename, the request-data / echo flags, the `$HOME`/exec commands, etc.) to produce the concrete script for this session.

**Code trace.** Still inside `bootstrap_script` `[kittens/ssh/main.go:422]`:

- The template is loaded from the embedded archive with `cd.bootstrap_script = utils.UnsafeBytesToString(shell_integration.Data()["shell-integration/ssh/bootstrap."+cd.script_type].Data)` `[kittens/ssh/main.go:481]` — i.e. `bootstrap.sh` when `script_type=="sh"`, `bootstrap.py` when `"py"`.
- Placeholders are substituted with `cd.bootstrap_script = prepare_script(cd.bootstrap_script, sd)` `[kittens/ssh/main.go:482]`.
- `prepare_script` `[kittens/ssh/main.go:407]` builds a single alternation regexp by wrapping each replacement key with `\b` word boundaries: `keys[i] = "\\b" + key + "\\b"` `[kittens/ssh/main.go:416]`, `pat := regexp.MustCompile(strings.Join(keys, "|"))` `[kittens/ssh/main.go:418]`, and replaces each match with its value `[kittens/ssh/main.go:419]`.
- The boolean flags are set just above via `add_bool(cd.request_data, "REQUEST_DATA")` and `add_bool(cd.echo_on, "ECHO_ON")` `[kittens/ssh/main.go:473-474]`, where `add_bool` writes `"1"` or `"0"`.

The remote templates confirm the placeholders being replaced: `request_data="REQUEST_DATA"` at `[shell-integration/ssh/bootstrap.sh:90]`, and in the Python variant `echo_on = int('ECHO_ON')` `[shell-integration/ssh/bootstrap.py:20]` and `request_data = int('REQUEST_DATA')` `[shell-integration/ssh/bootstrap.py:22]`.

**Observed evidence.** Running `get_remote_command` (which calls `bootstrap_script`) with the default interpreter and printing the substituted lines of the generated script:

```bash
go test -run TestBlitzyObserveEV4 -v ./kittens/ssh/     # temporary harness, since removed
```

```
EV4>>> bootstrap line: request_data="0"
EV4>>> bootstrap line: dcs_to_kitty "ssh" "id="REQUEST_ID":pwfile="PASSWORD_FILENAME":pw="DATA_PASSWORD""
```

The template's `request_data="REQUEST_DATA"` `[shell-integration/ssh/bootstrap.sh:90]` has been substituted to `request_data="0"` (this session did not request data over the tty). The `REQUEST_ID`/`PASSWORD_FILENAME`/`DATA_PASSWORD` placeholders on the `dcs_to_kitty` line are *left in place* here because, when `request_data` is false, the sensitive values are deliberately not merged into the substitution map (`sd` only receives them `if cd.request_data`, `[kittens/ssh/main.go:476-477]`).

**Rationale.** Keeping the remote script as a substituted template (rather than hand-assembled strings) keeps the shipped script auditable and identical across sessions except for the small set of named placeholders, and lets the same template serve both the "request data over tty" and "read data from shm" modes by toggling `REQUEST_DATA`.

## Q3 — Archive build and transport

**Mechanism.** All the files the remote side needs — the environment script, the remote-staging utilities, the shell-integration files for every supported shell, the `kitty`/`kitten` wrapper binaries, and the terminfo entries — are packed into a single **gzip-compressed PAX tar** archive. That archive is base64-encoded into the JSON payload (shared memory, Q1) and/or streamed over the tty framed by explicit start/end markers; the remote extracts it with `tar`.

**Code trace.** `make_tarfile` `[kittens/ssh/main.go:255]`:

- Compression: `gw, err := gzip.NewWriterLevel(&w, gzip.BestCompression)` `[kittens/ssh/main.go:259]`.
- Tar writer: `tw := tar.NewWriter(gw)` `[kittens/ssh/main.go:263]`, with every header using `Format: tar.FormatPAX` `[kittens/ssh/main.go:297]` (and again for embedded entries at `[kittens/ssh/main.go:310]`).
- Entries added: `data.sh` `[kittens/ssh/main.go:321]`; `bootstrap-utils.sh` only when `cd.script_type == "sh"` `[kittens/ssh/main.go:324-325]`; the shell-integration files `[kittens/ssh/main.go:329-340]`; the `kitty`/`kitten` wrappers plus a `version` file when `cd.host_opts.Remote_kitty != Remote_kitty_no` `[kittens/ssh/main.go:342-353]`; and terminfo `home/.terminfo/kitty.terminfo` `[kittens/ssh/main.go:355]` plus `home/.terminfo/x/<DefaultTermName>` `[kittens/ssh/main.go:357]`.
- The Go standard-library packages used are `archive/tar` `[kittens/ssh/main.go:6]`, `compress/gzip` `[kittens/ssh/main.go:8]`, `encoding/base64` `[kittens/ssh/main.go:9]`, and `encoding/json` `[kittens/ssh/main.go:10]`.
- Payload encoding: the whole tarball is base64-encoded with `base64.StdEncoding.EncodeToString(tfd)` `[kittens/ssh/main.go:440]` (the `"tarfile"` field of the JSON in Q1).

Transport (remote side, `shell-integration/ssh/bootstrap.sh`): bulk data is framed by `KITTY_DATA_START` `[shell-integration/ssh/bootstrap.sh:144]` … data … `KITTY_DATA_END` `[shell-integration/ssh/bootstrap.sh:99]`, terminated by an `OK` marker `[shell-integration/ssh/bootstrap.sh:141]`. Extraction is `read_base64_from_tty | base64_decode | command tar "xpzf" "-" "-C" "$tdir"` `[shell-integration/ssh/bootstrap.sh:113]` — the `z` in `xpzf` is gzip decompression, matching `gzip.NewWriterLevel` on the sending side.

## Q5 — Connection reuse decision (SSH `ControlMaster` / connection sharing / control path)

**Mechanism.** The kitten uses OpenSSH connection multiplexing. It always emits the control-socket options; then, if connection sharing is enabled *and* a master connection is already alive, it skips the expensive out-of-band data request and simply piggybacks on the existing master.

**Code trace.** `connection_sharing_args(kitty_pid int)` `[kittens/ssh/main.go:121]` emits:

- `-o ControlMaster=auto` `[kittens/ssh/main.go:138]`
- `-o ControlPath=` + `filepath.Join(rd, cp)` `[kittens/ssh/main.go:139]`
- `-o ControlPersist=yes` `[kittens/ssh/main.go:140]`
- plus `-o ServerAliveInterval=60` `[main.go:141]`, `-o ServerAliveCountMax=5` `[main.go:142]`, `-o TCPKeepAlive=no` `[main.go:143]`.

The control-path filename comes from the generated template: `cp := strings.Replace(kitty.SSHControlMasterTemplate, "{kitty_pid}", strconv.Itoa(kitty_pid), 1)` `[kittens/ssh/main.go:135]`, then `cp = strings.Replace(cp, "{ssh_placeholder}", "%C", 1)` `[kittens/ssh/main.go:136]`, where `SSHControlMasterTemplate = "kssh-{kitty_pid}-{ssh_placeholder}"` (EV2). The `%C` is OpenSSH's own hash-of-connection-parameters token.

A long-runtime-dir workaround guards the ~104-char socket-path limit: `if len(rd) > 35 { idiotic_design := fmt.Sprintf("/tmp/kssh-rdir-%d", os.Geteuid()); … rd = idiotic_design }` `[kittens/ssh/main.go:128-133]`, symlinking the runtime dir to a short `/tmp` path.

The reuse decision in `run_ssh`: the master-liveness probe is `master_is_functional := func() bool { … check_cmd := slices.Insert(cmd, 1, "-O", "check"); master_is_alive = exec.Command(check_cmd[0], check_cmd[1:]...).Run() == nil; … }` `[kittens/ssh/main.go:653-659]` — i.e. it runs `ssh -O check`. The gate is:

```go
if need_to_request_data && host_opts.Share_connections && master_is_functional() {
    need_to_request_data = false
}
```

`[kittens/ssh/main.go:663-664]`. When forwarding remote control (or otherwise needing a master), `run_control_master` `[kittens/ssh/main.go:666]` starts one explicitly with `-N -f` (`cmcmd = append(cmcmd, "-N", "-f")` `[kittens/ssh/main.go:669]`).

**Observed evidence.** Calling `connection_sharing_args(424242)`:

```bash
go test -run TestBlitzyObserveEV3 -v ./kittens/ssh/     # temporary harness, since removed
```

```
-o ControlMaster=auto -o ControlPath=/root/.cache/kitty/run/kssh-424242-%C -o ControlPersist=yes -o ServerAliveInterval=60 -o ServerAliveCountMax=5 -o TCPKeepAlive=no
```

The emitted `ControlPath` is `…/kssh-424242-%C`: the `{kitty_pid}` slot became `424242` (the pid I passed) and `{ssh_placeholder}` became the literal `%C`, exactly per `[kittens/ssh/main.go:135-136]`. All three of `-o ControlMaster=auto`, `-o ControlPath=…`, and `-o ControlPersist=yes` are present.

**Rationale.** `ControlMaster=auto` means "reuse an existing master if one exists, otherwise become the master"; subsequent sessions ride the existing socket and skip the TCP + cryptographic handshake, and the control socket is a filesystem object protected by its permissions. (These OpenSSH semantics are framing — see "What is framing vs. observed" at the end; the *authoritative* facts here are the exact directives the kitten emits, shown above, and the `ssh -O check` gate.) Skipping the data request when a master is alive is the concrete performance win: no second credential exchange is needed for piggybacked sessions.

## Q6 — Per-shell bootstrap encoding

**Mechanism.** `sshd` runs the command by joining the argv with spaces and passing it as one string to the user's login shell with `-c`. Since that login shell may have non-POSIX quoting, the kitten keeps the command shape trivially simple — `interpreter -c <unwrap_script> <encoded_bootstrap>` — and picks one of **two** encodings depending on whether the remote interpreter is Python or a POSIX shell. Then, *on the remote side*, a second layer chooses per-shell integration when the login shell is re-executed.

## Q8 — Shared-memory security rationale

**Mechanism.** The shared-memory object is created owner-only and exclusively, its owner and permissions are re-verified on read, and it is destroyed after a single read. Together these keep the credential off `argv`/env and minimize how long it can be read by anyone.

**Code trace.**

- **Read-once.** `read_data_from_shared_memory` `[kittens/ssh/main.go:72]` calls `shm.ReadWithSizeAndUnlink` `[tools/utils/shm/shm.go:142]`. That function runs the file callbacks, then `defer func() { mmap.Close(); _ = mmap.Unlink() }()` `[tools/utils/shm/shm.go:159-162]` — so the object is unlinked (name removed) immediately after the single read completes.
- **Owner check.** The callback in `read_data_from_shared_memory` enforces `if os.Getuid() != int(stat.Uid) || os.Getgid() != int(stat.Gid) { return fmt.Errorf("Incorrect owner on SHM file") }` `[kittens/ssh/main.go:74-76]`.
- **Permission check.** `if s.Mode().Perm() != 0o600 { return fmt.Errorf("Incorrect permissions on SHM file") }` `[kittens/ssh/main.go:79-80]`.
- **Exclusive create at `0600`.** The object is created with `os.OpenFile(path, os.O_EXCL|os.O_CREATE|os.O_RDWR, 0600)` `[tools/utils/shm/shm_fs.go:130]` — `O_EXCL|O_CREATE` guarantees a fresh object (no pre-existing file is reused).
- **Location.** On Linux the backing dir is `const SHM_DIR = "/dev/shm"` `[tools/utils/shm/specific_linux.go:11]`.

**Observed evidence.** The same EV6 capture demonstrates all three security properties at once:

```bash
go test -run TestBlitzyObserveEV6 -v ./kittens/ssh/     # temporary harness, since removed
```

```
EV6>>> stat /dev/shm/kssh-40398-FZFPPIJG726JE -> -rw------- mode=0600
EV6>>> read #1: ok=true bytes=32179
EV6>>> read #2 (after unlink): err=open /dev/shm/kssh-40398-FZFPPIJG726JE: no such file or directory
```

The `stat` shows `-rw-------` / `mode=0600`, matching the `0600` create at `[tools/utils/shm/shm_fs.go:130]` and the `!= 0o600` guard at `[kittens/ssh/main.go:79-80]`. The object lives under `/dev/shm` per `[tools/utils/shm/specific_linux.go:11]`. The first read succeeds; the second fails with `no such file or directory` — direct proof of the read-once unlink at `[tools/utils/shm/shm.go:159-162]`.

**Rationale.** Because the secret is in an owner-only shm object (not `argv`/env, which are world-visible via `/proc`), and because it is destroyed after one read, another local process has only a tiny window in which even the *owner*'s objects could be read — and cross-user reads are rejected by the owner/permission checks. (The generic POSIX `shm_open(3)`/`shm_overview(7)` semantics — named object with owner + mode bits, `shm_unlink` removing the name so later opens fail — are external framing; the authoritative facts here are the exact `0600`, `O_EXCL|O_CREATE`, the two `Errorf` guards, and the observed second-read failure.)

## Q9 — TTY request/response protocol (DCS escape codes)

**Mechanism.** The kitten and the remote bootstrap talk over the controlling tty using Kitty's private DCS (Device Control String) escape sequences. The local side tells kitty (the terminal) "here is the request id, the shm object name, and the password" so kitty can service the remote's data request; the remote side emits the mirror-image request. Bulk data is sent framed by text markers.

**Code trace — local.** In `run_ssh`, only when `!cd.request_data` `[kittens/ssh/main.go:761]`, it builds `rq := fmt.Sprintf("id=%s:pwfile=%s:pw=%s", cd.replacements["REQUEST_ID"], cd.replacements["PASSWORD_FILENAME"], cd.replacements["DATA_PASSWORD"])` `[kittens/ssh/main.go:762]`, then `dcs, err = tui.DCSToKitty("ssh", rq)` `[kittens/ssh/main.go:766]` and `term.WriteAllString(dcs)` `[kittens/ssh/main.go:768]`. `DCSToKitty` `[tools/tui/dcs_to_kitty.go:14]` base64-encodes the payload `[tools/tui/dcs_to_kitty.go:15]` and builds `ans := "\x1bP@kitty-" + msgtype + "|" + data` `[tools/tui/dcs_to_kitty.go:16]`, terminated (non-tmux) with `ans += "\033\\"` (ESC `\` = ST) `[tools/tui/dcs_to_kitty.go:25]`.

**Code trace — remote.** `shell-integration/ssh/bootstrap.sh` defines `dcs_to_kitty() { printf "\033P@kitty-$1|%s\033\134" "$(printf "%s" "$2" | base64_encode)" > /dev/tty; }` `[bootstrap.sh:75]` — the same `\033P@kitty-…|<base64>\033\134` frame (`\134` is `\`). It emits the request only when `request_data="1"` `[bootstrap.sh:90-95]`, after `command stty "-echo" < /dev/tty` `[bootstrap.sh:93]`, as `dcs_to_kitty "ssh" "id="REQUEST_ID":pwfile="PASSWORD_FILENAME":pw="DATA_PASSWORD""` `[bootstrap.sh:94]`. Because `base64` may be missing, the remote has a fallback chain: `base64` `[bootstrap.sh:55-57]` → `openssl` `[bootstrap.sh:58-60]` → `b64encode` `[bootstrap.sh:61-63]` → python `[bootstrap.sh:64-67]` → perl `[bootstrap.sh:68-70]` → else `die "base64 executable not present on remote host, ssh kitten cannot function."` `[bootstrap.sh:72]`. Bulk data reply is framed by `KITTY_DATA_START`/`KITTY_DATA_END`/`OK` `[bootstrap.sh:137-155]`. After the child exits, the local side calls `drain_potential_tty_garbage` `[kittens/ssh/main.go:530]` (invoked at `[kittens/ssh/main.go:783]`).

The frame is exactly `\x1bP` (DCS) + `@kitty-ssh|` + base64 + `\x1b\\` (ESC `\` = ST), matching `[tools/tui/dcs_to_kitty.go:16,25]`. Decoding the base64 recovers the `id=%s:pwfile=%s:pw=%s` payload built at `[kittens/ssh/main.go:762]`:

## What is framing vs. observed (limits of verification)

Everything quoted in the "Observed evidence" blocks was produced by running code in *this* repository and is reproducible with the commands shown. Two categories of statement are **framing**, not observations of this repo, and are labeled as such where they appear:

- **OpenSSH multiplexing semantics** (Q5): the meaning of `ControlMaster=auto`/`ControlPath`/`ControlPersist` (reuse-or-become-master, piggybacking sessions skipping the TCP + crypto handshake, the control socket being a permission-protected Unix-domain socket) is standard OpenSSH behavior. This document verifies only that the kitten *emits* those exact directives (EV3) and probes liveness with `ssh -O check` `[kittens/ssh/main.go:658]`; it does not measure a live master handshake (no SSH server is involved in the evidence).
- **POSIX shared-memory semantics** (Q8): the general `shm_open(3)`/`shm_overview(7)` model (named object with owner + mode bits; `shm_unlink` removing the name so later opens fail) is standard POSIX. This document verifies the kitten's concrete use of it — `0600`, `O_EXCL|O_CREATE`, the owner/permission guards, and the observed second-read failure after unlink (EV6).

One representation detail, not a discrepancy: the `rcmd[0..3]` line in EV4 is Go's `%q` rendering, so each backslash in the `tr` unwrap literal `[kittens/ssh/main.go:506]` prints doubled; the underlying string is the source literal unchanged. Dynamic values (pid, shm suffix, exact byte counts, and the `go1.22.12` patch version) are specific to this run; the literals and structure are stable across runs.
