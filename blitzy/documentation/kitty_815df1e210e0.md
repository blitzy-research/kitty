## Section 1 — Which language does the runtime heavy lifting, and where does performance come from? (OBJ-1)

**Direct answer.** **Python is the control / orchestration layer; the performance-critical work runs in native C — compiled into a single CPython extension, `kitty.fast_data_types` — and on the GPU via GLSL shaders.** kitty's speed therefore comes from the native core plus GPU offload, not from Python. The Python you see under `kitty/*.py` wires the program together (argument parsing, config, layout policy, glue), while the hot paths (VT parsing, the screen/grid model, GPU rendering, font rasterization, and the PTY I/O loop) live in the C extension and the shaders. Go (`tools/`) is a large, mostly *independent* body that is compiled into a separate `kitten` binary and does not run inside the terminal's per-frame hot loop.

### 1.2 The runtime wiring: a native launcher boots CPython, which loads the C core

kitty ships a **native C launcher** that embeds a CPython interpreter and then hands control to Python, which in turn imports the compiled C core. The launcher constructs the extension directory and Python home and boots the interpreter:

```text
kitty/launcher/main.c
147: run_embedded(RunData *run_data) {
148:     bypy_pre_initialize_interpreter(false);
155:     int num = snprintf(extensions_dir_full, PATH_MAX, "%s/%s/kitty-extensions", run_data->exe_dir, python_relpath);
161:     num = snprintf(python_home_full, PATH_MAX, "%s/%s/python%s", run_data->exe_dir, python_relpath, PYVER);
```

The C core that Python loads is **one** CPython extension module, defined by a single `PyModuleDef` whose name is `fast_data_types`:

```text
kitty/data-types.c
467: static struct PyModuleDef module = {
468:     .m_base = PyModuleDef_HEAD_INIT,
469:     .m_name = "fast_data_types",   /* name of module */
470:     .m_doc = NULL,
471:     .m_size = -1,
472:     .m_methods = module_methods
```

There are **49** top-level C translation units (`ls kitty/*.c | wc -l` → 49) — e.g. `screen.c`, `graphics.c`, `shaders.c`, `fonts.c`, `child-monitor.c`, `vt-parser.c`, `simd-string-128.c`, `simd-string-256.c` — and they all register their functions and constants into that **single** `fast_data_types` module. That is why Sections 3 and 4 both collapse onto the same missing `.so`: it is the one native object the whole Python layer (and the kittens) import from.

## Section 2 — What role do the GLSL shader files play, and how central are they? (OBJ-2)

**Direct answer.** The **13** `kitty/*.glsl` files **are** the "GPU accelerated" rendering pipeline. They are not decoration or an optional feature — they are the actual programs kitty uploads to and runs on the GPU to draw everything you see: the terminal grid (text + cursor), window/pane borders, inline images, background images, and the window tint overlay. They are bundled into the build and are compiled and *linked into OpenGL programs at runtime*, once per OS window at startup. If they fail to link, kitty raises an error and cannot render — that is how central they are.

### 2.1 Enumerating all 13 shader files (measured)

```text
$ wc -l kitty/*.glsl
   22 kitty/alpha_blend.glsl
   14 kitty/bgimage_fragment.glsl
   48 kitty/bgimage_vertex.glsl
    6 kitty/border_fragment.glsl
   48 kitty/border_vertex.glsl
   31 kitty/cell_defines.glsl
  204 kitty/cell_fragment.glsl
  233 kitty/cell_vertex.glsl
   27 kitty/graphics_fragment.glsl
   24 kitty/graphics_vertex.glsl
   15 kitty/linear2srgb.glsl
    6 kitty/tint_fragment.glsl
   18 kitty/tint_vertex.glsl
  696 total
```

That is **five vertex/fragment pairs** (ten files) that become GPU programs, plus **three shared `#include` helpers** (`cell_defines.glsl`, `alpha_blend.glsl`, `linear2srgb.glsl`). The largest by far are the cell shaders (`cell_vertex.glsl` 233 lines, `cell_fragment.glsl` 204 lines) — the terminal-grid path, which is the core hot path.

### 2.2 Shader-to-role mapping (every file named)

| Shader pair / file | Rendering responsibility |
|---|---|
| `cell_vertex.glsl` + `cell_fragment.glsl` | Terminal grid: glyph/text + cursor rendering (the core hot path) |
| `border_vertex.glsl` + `border_fragment.glsl` | Window/pane border decoration |
| `graphics_vertex.glsl` + `graphics_fragment.glsl` | Graphics-protocol inline image compositing |
| `bgimage_vertex.glsl` + `bgimage_fragment.glsl` | Background image rendering |
| `tint_vertex.glsl` + `tint_fragment.glsl` | Window tint overlay |
| `cell_defines.glsl`, `alpha_blend.glsl`, `linear2srgb.glsl` | Shared `#include` helpers: common defines, alpha blending, sRGB↔linear color conversion (not standalone programs) |

The helper classification is grounded in code, not guessed (see 2.4): the build's shader loop keys on the `_vertex` / `_fragment` suffix, and the Python shader layer resolves `#include` directives — the three helpers have no `_vertex`/`_fragment` suffix and are pulled in via `#include` by the real shaders.

### 2.3 Build-time bundling of the shaders

`setup.py` globs every `kitty/*.glsl` at build time and classifies the vertex/fragment stages:

```text
kitty/setup.py
1040:     for x in sorted(glob.glob('kitty/*.glsl')):
1041:         name = os.path.basename(x).partition('.')[0]
1042:         name, sep, shader_type = name.partition('_')
1043:         if not sep or shader_type not in ('fragment', 'vertex'):
1044:             continue
```

The `continue` at `setup.py:1043-1044` skips any file whose name has no `_vertex`/`_fragment` suffix — i.e. `cell_defines`, `alpha_blend`, `linear2srgb` — confirming those three are not standalone shader stages but shared includes.

### 2.4 Runtime: GLSL is compiled and linked into OpenGL programs

The Python shader layer imports the program-id constants and the native `compile_program` entry point from the C core, prepends the GLSL version, and resolves `#include`s:

```text
kitty/shaders.py
10: from .fast_data_types import (
11:     BGIMAGE_PROGRAM,
...
19:     GLSL_VERSION,
...
30:     compile_program,
...
61:     def _load_sources(self, name: str, seen: Set[str], level: int = 0) -> Iterator[str]:
62:         if level == 0:
63:             yield f'#version {GLSL_VERSION}\n'
...
72:             yield from self._load_sources(iname, seen, level+1)
...
87:     def compile(self, program_id: int, allow_recompile: bool = False) -> None:
...
90:             compile_program(program_id, self.vertex_sources, self.fragment_sources, allow_recompile)
...
107: @lru_cache(maxsize=64)
108: def program_for(name: str) -> Program:
109:     return Program(name)
```

`shaders.py:63` prepends `#version {GLSL_VERSION}` and `shaders.py:72` recursively resolves `#include` directives (this is the mechanism by which the three helper files are pulled into the cell/border/graphics/etc. shaders). `shaders.py:90` then calls the native `compile_program`. On the C side, that native function compiles each stage and links the GPU program:

```text
kitty/shaders.c
1153: attach_shaders(PyObject *sources, GLuint program_id, GLenum shader_type) {
1160:     GLuint shader_id = compile_shaders(shader_type, PyTuple_GET_SIZE(sources), c_sources);
1168: compile_program(PyObject UNUSED *self, PyObject *args) {
1182:     glLinkProgram(program->id);
1189:         PyErr_Format(PyExc_ValueError, "Failed to link GLSL shaders:\n%s", glbuf);
...
1254:     C(GLSL_VERSION);
```

So the full pipeline is: **`Program.compile` (`shaders.py:90`) → native `compile_program` (`shaders.c:1168`) → `attach_shaders` (`shaders.c:1153`) → `compile_shaders` (`shaders.c:1160`, per stage) → `glLinkProgram` (`shaders.c:1182`)**, i.e. GLSL source is turned into linked OpenGL GPU programs at runtime. A link failure surfaces as `Failed to link GLSL shaders` at `shaders.c:1189`. `shaders.c:1254` registers `GLSL_VERSION` (alongside the program-id constants `CELL_PROGRAM`, `BORDERS_PROGRAM`, `GRAPHICS_PROGRAM`, `BGIMAGE_PROGRAM`, `TINT_PROGRAM`, …) into the same `fast_data_types` module.

### 2.5 Centrality and honest labeling

- **Directly observed:** the 13 files and their line counts; the build glob and vertex/fragment filter (`setup.py:1040-1044`); the Python `#version`/`#include` handling and the call into native `compile_program` (`shaders.py:63,72,90,108`); the native compile-and-link path and the link-error message (`shaders.c:1160,1182,1189`); and that the program-id constants + `GLSL_VERSION` are exposed by the native module (`shaders.py:10-30`, `shaders.c:1254`).
- **(Inferred)** that each program is (re)compiled at OS-window creation for *every* window: the code path and the `@lru_cache(maxsize=64)` on `program_for` (`shaders.py:107-108`) plus `allow_recompile` on `Program.compile` (`shaders.py:87`) indicate per-window/on-demand program creation with caching. A full GPU trace was not captured here (this environment renders via software `llvmpipe`), so the "every window" timing is labeled Inferred; the compile/link *code path itself* is directly quoted above.

## Section 3 — What is missing when the entry point is run directly, and how is Python wired to the native core? (OBJ-3)

**Direct answer.** The **one critical piece that everything depends on is the compiled C extension module `kitty.fast_data_types`** (the `kitty/fast_data_types.so` produced by the build). In a fresh, unbuilt checkout that `.so` does not exist, so the very first import that reaches it fails, and Python never gets anywhere near terminal-startup logic. Build it (`python3 setup.py`) and the same entry point runs.

First, the unbuilt state is real: the `.so` is absent while the type stub `.pyi` is present (which is why editors/type-checkers can see the API even though `import` fails at runtime until built).

## Section 4 — Are the kittens truly independent, or do they rely on the same native bridge? (OBJ-4)

**Direct answer.** **No — the kittens are not independent.** They look like small, self-contained tools, but they transitively depend on the **same** `kitty.fast_data_types` native bridge. Exercised standalone in the unbuilt tree, a kitten fails on the identical `ModuleNotFoundError` as the terminal itself — and it reaches that failure through **two different routes**, proving the coupling is structural, not incidental.

- **Directly observed:** both standalone failure paths and their full tracebacks; both import chains quoted line-by-line; the direct native import in the shared TUI layer (`handler.py:10`); and the post-build success of path (b) plus a working `monotonic()`.
